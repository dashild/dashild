Este tutorial construye [examples/vet-clinic](https://github.com/dashild/dashild/tree/main/examples/vet-clinic):
un pequeño SaaS para clínicas veterinarias. Cada clínica es un tenant; el
personal, los dueños, las mascotas, las citas, las visitas y las vacunas están
aislados por clínica.

Está escrito para alguien que sabe JavaScript o TypeScript y es nuevo en
Dashild. Cada paso explica qué hace el comando o el fichero, no solo qué pegar.

Qué vas a aprender:

- Cómo un modelo de Prisma se convierte en un recurso de Dashild.
- Cómo funciona el aislamiento por tenant en el servidor.
- Cómo los roles deciden qué acciones aparecen.
- Cómo encajan relaciones, filtros, celdas custom y handlers de acciones.

La app terminada está en el repositorio para comparar.

## 1. Crear la app

```bash
pnpm create dashild@latest vet-clinic --tenancy --database sqlite --yes
cd vet-clinic
```

El scaffolder crea una app Next.js, instala Dashild y prepara el panel.
`--tenancy` añade las piezas multi-tenant:

- Un modelo `Organization` (una fila por clínica).
- `User.organizationId` y `User.role`.
- `src/lib/organization.ts`: qué clínicas ve el usuario y cuál está activa.
- `src/lib/session.ts`: `getCurrentUser()` devuelve la clínica activa.
- `src/dashild/organization-actions.ts`: la server action del selector.
- La ruta de montaje pasa las clínicas y el selector al panel.

`--database sqlite` mantiene el ejemplo autocontenido: la base de datos es un
fichero (`prisma/dev.db`), así que no necesitas un servidor.

`BETTER_AUTH_URL` debe coincidir con la URL que abres en el navegador. El
scaffold pone `http://localhost:3000`.

En este punto `pnpm dev` ya funciona, con el panel vacío. Lo vamos a llenar.

## 2. Modelar la clínica

`prisma/schema.prisma` describe las tablas de la base de datos. Prisma lee este
fichero y genera un cliente tipado; Dashild lee los metadatos generados para
saber qué campos tiene cada modelo.

La tenencia ya creó `Organization` y el enum `Role`. Añade `VET` y `RECEPTION`
al enum y las relaciones inversas que Prisma necesita para las tablas nuevas:

```prisma title="prisma/schema.prisma"
enum Role {
  ADMIN
  VET
  RECEPTION
  USER
}

model User {
  // ...los campos de Better Auth...
  organizationId String?
  organization   Organization? @relation(fields: [organizationId], references: [id], onDelete: SetNull)
  role           Role      @default(USER)
  vetAppointments Appointment[] @relation("VetAppointments")
  vetVisits       Visit[]       @relation("VetVisits")
}

model Organization {
  id    String @id @default(uuid())
  name  String
  users User[]

  owners       Owner[]
  pets         Pet[]
  appointments Appointment[]
  visits       Visit[]
  vaccinations Vaccination[]
}
```

Después añade los modelos de dominio:

```prisma title="prisma/schema.prisma"
enum Species {
  DOG
  CAT
  RABBIT
  BIRD
  OTHER
}

enum AppointmentStatus {
  SCHEDULED
  ATTENDED
  CANCELLED
}

model Owner {
  id             String       @id @default(uuid())
  name           String
  email          String?
  phone          String?
  organizationId String
  organization   Organization @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  pets           Pet[]
  createdAt      DateTime     @default(now())
  updatedAt      DateTime     @updatedAt

  @@index([organizationId])
}

model Pet {
  id             String        @id @default(uuid())
  name           String
  species        Species       @default(DOG)
  breed          String?
  birthDate      DateTime?
  photo          Bytes?
  ownerId        String
  owner          Owner         @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  organizationId String
  organization   Organization  @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  appointments   Appointment[]
  visits         Visit[]
  vaccinations   Vaccination[]
  createdAt      DateTime      @default(now())
  updatedAt      DateTime      @updatedAt

  @@index([ownerId])
  @@index([organizationId])
}

model Appointment {
  id             String            @id @default(uuid())
  startsAt       DateTime
  reason         String
  status         AppointmentStatus @default(SCHEDULED)
  petId          String
  pet            Pet               @relation(fields: [petId], references: [id], onDelete: Cascade)
  vetId          String?
  vet            User?             @relation("VetAppointments", fields: [vetId], references: [id], onDelete: SetNull)
  organizationId String
  organization   Organization      @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  createdAt      DateTime          @default(now())
  updatedAt      DateTime          @updatedAt

  @@index([petId])
  @@index([organizationId])
  @@index([startsAt])
}

model Visit {
  id             String       @id @default(uuid())
  visitedAt      DateTime     @default(now())
  reason         String
  diagnosis      String?
  notes          String?
  petId          String
  pet            Pet          @relation(fields: [petId], references: [id], onDelete: Cascade)
  vetId          String?
  vet            User?        @relation("VetVisits", fields: [vetId], references: [id], onDelete: SetNull)
  organizationId String
  organization   Organization @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  createdAt      DateTime     @default(now())
  updatedAt      DateTime     @updatedAt

  @@index([petId])
  @@index([organizationId])
}

model Vaccination {
  id             String       @id @default(uuid())
  name           String
  appliedAt      DateTime     @default(now())
  nextDueAt      DateTime?
  petId          String
  pet            Pet          @relation(fields: [petId], references: [id], onDelete: Cascade)
  organizationId String
  organization   Organization @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  createdAt      DateTime     @default(now())

  @@index([petId])
  @@index([organizationId])
}
```

Fíjate en varias cosas:

- `organizationId` se repite en los datos de la clínica. Parece redundante, pero
  hace que los filtros por tenant y los índices sean simples y rápidos.
- `Pet.owner` es una relación con `Owner`; `Appointment.pet` es una relación con
  `Pet`. Dashild usa esas relaciones para columnas, formularios y relation
  managers.
- `photo Bytes?` guarda la imagen en la base de datos en este ejemplo. En una
  app real normalmente guardarías una URL.

## 4. Generar el primer recurso (Owners)

Un recurso es un fichero de datos. Dice qué modelo mostrar, qué columnas y
campos de formulario usar y qué política lo protege. Dashild tiene una ruta para
todos los recursos; no hay páginas que generar.

```bash
pnpm dashild make:resource Owner
```

El comando recibe el nombre del modelo de Prisma, en singular: `Owner`, no
`Owners`.

`make:resource` lee `dashild-metadata.json`, el fichero que escribe el generador
de Prisma, y:

1. Escribe `src/dashild/resources/owner.ts` con columnas y campos de formulario
   inferidos del modelo.
2. Registra el recurso en `src/dashild/panel.ts`.
3. Añade una entrada **fail-closed** en `src/dashild/policies.ts`
   (`scope: () => null`), así que no se ve nada hasta que definas la política.

El fichero es write-once: si ejecutas el comando otra vez, no sobrescribe tu
trabajo.

Abre el fichero generado y ajústalo hasta que quede así:

```ts title="src/dashild/resources/owner.ts"
import { defineResource } from "@dashild/core";

export const ownerResource = defineResource({
  model: "Owner",
  navigation: { label: "Owners", slug: "owners", group: "Clinic", icon: "users" },
  table: {
    searchable: ["name", "email", "phone"],
    pageSize: 25,
    columns: [
      { field: "name", sortable: true },
      { field: "email", sortable: true },
      { field: "phone" },
      { field: "createdAt", format: "datetime", sortable: true },
    ],
  },
  form: {
    fields: [
      { field: "name", type: "text", rules: { required: true } },
      { field: "email", type: "email" },
      { field: "phone", type: "text" },
    ],
  },
  policy: { scope: "organization" },
});
```

`searchable` lista los campos del buscador. `policy: { scope: "organization" }`
es un marcador: el filtro real vive en `policies.ts`, que escribimos en el paso 8.

## 5. Generar el resto de recursos

Los demás siguen el mismo comando. Ejecútalos ahora:

```bash
pnpm dashild make:resource Pet
pnpm dashild make:resource Appointment
pnpm dashild make:resource Visit
pnpm dashild make:resource Vaccination
pnpm dashild make:resource User
```

Luego personaliza cada fichero. `Pet` y `Appointment` se explican abajo;
`Visit`, `Vaccination` y `User` siguen la misma forma y están enlazados al
final. La versión generada es un punto de partida; las columnas, filtros y
campos son datos tuyos.

:::note
`make:resource User` escribe `user.ts`. El ejemplo lo renombra a `staff.ts`
porque solo edita personal (nombre y rol), y actualiza el import en `panel.ts`.
Renombrar un fichero es válido si el panel importa la ruta nueva.
:::

## 6. Mascotas y una celda custom

El recurso de mascotas que generaste en el paso 5 necesita una celda custom. El
modelo `Pet` tiene una columna `species`, pero `DOG`/`CAT` no es amable en una
tabla. Una **celda** es un componente React pequeño que renderiza el valor de
una columna. El shell trae algunas plantillas; copia una y adáptala en vez de
empezar de cero:

```bash
pnpm dashild ui:add avatar-cell --dir src/components/dashild
```

`ui:add` copia la plantilla a `src/components/dashild/` (la carpeta por defecto
es `components/dashild`, así que `--dir` la apunta al árbol `src/` de la app) e
imprime la línea `registerCell(...)` que necesitas. No edita el registry por ti: el nombre del
componente y la ruta del import son decisión tuya.

Renombra el fichero copiado a `species-cell.tsx` y sustituye su contenido:

```tsx title="src/components/dashild/species-cell.tsx"
"use client";

import type { CellRendererProps } from "@dashild/admin";

const SPECIES: Record<string, { label: string; emoji: string }> = {
  DOG: { label: "Dog", emoji: "🐶" },
  CAT: { label: "Cat", emoji: "🐱" },
  RABBIT: { label: "Rabbit", emoji: "🐰" },
  BIRD: { label: "Bird", emoji: "🐦" },
  OTHER: { label: "Other", emoji: "🐾" },
};

/** Custom cell: species with an emoji instead of the raw enum value. */
export function SpeciesCell({ value }: CellRendererProps) {
  const species = SPECIES[String(value)] ?? {
    label: String(value ?? ""),
    emoji: "🐾",
  };

  return (
    <span className="inline-flex items-center gap-1.5">
      <span aria-hidden="true">{species.emoji}</span>
      {species.label}
    </span>
  );
}
```

Regístrala. El registro ocurre en cliente, porque los componentes son funciones
y no pueden viajar como props desde un componente de servidor:

```tsx title="src/dashild/registry.tsx"
"use client";

import {
  registerCell,
  registeredCells,
  registeredFields,
} from "@dashild/core";
import { RegistryProvider, type Registry } from "@dashild/admin";

import { SpeciesCell } from "../components/dashild/species-cell";

registerCell("species", SpeciesCell);

export function AppRegistryProvider({ children }: { children: React.ReactNode }) {
  return (
    <RegistryProvider
      cells={registeredCells() as Registry["cells"]}
      fields={registeredFields() as Registry["fields"]}
    >
      {children}
    </RegistryProvider>
  );
}
```

Por último, usa `cell: "species"` en el recurso de mascotas e incluye el campo
de foto:

## 7. Citas, filtros y acciones

El recurso de citas añade filtros y acciones:

```ts title="src/dashild/resources/appointment.ts"
import { defineResource } from "@dashild/core";

export const appointmentResource = defineResource({
  model: "Appointment",
  navigation: {
    label: "Appointments",
    slug: "appointments",
    group: "Clinic",
    icon: "calendar",
  },
  table: {
    searchable: ["reason"],
    pageSize: 25,
    columns: [
      { field: "startsAt", format: "datetime", sortable: true },
      { field: "pet", display: "name", sortable: true },
      { field: "vet", display: "name" },
      { field: "reason" },
      {
        field: "status",
        format: "badge",
        tone: { SCHEDULED: "accent", ATTENDED: "green", CANCELLED: "danger" },
      },
    ],
    filters: [
      { field: "status", type: "enum", label: "Status" },
      { field: "pet", type: "relation", label: "Pet", display: "name" },
      { field: "vet", type: "relation", label: "Vet", display: "name" },
    ],
    actions: [
      { name: "create", placement: "header" },
      { name: "view", placement: "row" },
      { name: "edit", placement: "row" },
      { name: "delete", placement: "row" },
      {
        name: "attend",
        label: "Mark attended",
        placement: "row",
        requires: "attend",
        variant: "secondary",
      },
      {
        name: "cancelAppointment",
        label: "Cancel",
        placement: "row",
        requires: "cancelAppointment",
        variant: "destructive",
        confirm: true,
      },
    ],
  },
  form: {
    fields: [
      { field: "startsAt", type: "datetime", rules: { required: true } },
      {
        field: "pet",
        type: "relation",
        relation: "pet",
        display: "name",
        rules: { required: true },
      },
      {
        field: "vet",
        type: "relation",
        relation: "vet",
        display: "name",
      },
      { field: "reason", type: "text", rules: { required: true } },
      { field: "status", type: "select" },
    ],
  },
  policy: { scope: "organization" },
});
```

Dos reglas importan aquí:

- Declarar `table.actions` **sustituye** las acciones integradas
  create/view/edit/delete, así que el recurso las lista explícitamente y luego
  añade las suyas.
- No llames `cancel` a una acción propia: es una acción integrada de formulario
  y el panel ignoraría la tuya. El ejemplo usa `cancelAppointment`.

`filters` renderiza la barra sobre la tabla. Las opciones de `status` vienen del
enum de Prisma; las de `pet` y `vet` se cargan en el servidor y se filtran por la
clínica activa.

## 8. Políticas y roles

`make:resource` añadió una entrada fail-closed por cada modelo. Sustituye
`policies.ts` por las reglas reales:

```ts title="src/dashild/policies.ts"
import {
  definePolicies,
  hasRole,
  type CurrentUser,
} from "@dashild/core";

const orgScope = (ctx: { organizationId: string | null }) =>
  ctx.organizationId ? { organizationId: ctx.organizationId } : null;

const admin = (ctx: { roles: string[] }) => hasRole(ctx, "ADMIN");
const clinical = (ctx: { roles: string[] }) =>
  hasRole(ctx, "ADMIN", "VET");
const staff = (ctx: { roles: string[] }) =>
  hasRole(ctx, "ADMIN", "VET", "RECEPTION");

/**
 * Every resource is scoped to the active clinic. A session without an
 * organization (for example, right after sign-up) sees nothing.
 */
export const policies = definePolicies<CurrentUser>({
  resources: {
    Owner: {
      scope: orgScope,
      can: { create: staff, update: staff, delete: admin },
    },
    Pet: {
      scope: orgScope,
      can: { create: staff, update: staff, delete: admin },
    },
    Appointment: {
      scope: orgScope,
      can: {
        create: staff,
        update: staff,
        delete: admin,
        attend: clinical,
        cancelAppointment: (ctx) => hasRole(ctx, "ADMIN", "RECEPTION"),
      },
    },
    Visit: {
      scope: orgScope,
      can: { create: clinical, update: clinical, delete: admin },
    },
    Vaccination: {
      scope: orgScope,
      can: { create: clinical, update: clinical, delete: admin },
    },
    User: {
      scope: orgScope,
      can: { create: () => false, update: admin, delete: () => false },
    },
  },
});
```

Cómo leerlo:

- `scope` es un `where` de Prisma que se aplica en el servidor a cada lectura y
  escritura. Devolver `null` deniega el recurso, así que una sesión sin clínica
  no ve nada.
- `can` decide los permisos. `ADMIN`, `VET` y `RECEPTION` son cadenas que vienen
  de `User.role`; los nombres los define la app.
- Las acciones declaradas (`attend`, `cancelAppointment`) son deny-by-default:
  si falta el predicado, la acción se oculta y el servidor la rechaza.

## 9. Handlers de acciones

El recurso declara la acción; el handler se ejecuta en el servidor:

```ts title="src/dashild/actions/index.ts"
import type { ActionHandler, CurrentUser } from "@dashild/core";

type AppointmentStatus = "ATTENDED" | "CANCELLED";

interface ScopedAppointmentClient {
  appointment: {
    update(args: {
      where: { id: string };
      data: { status: AppointmentStatus };
    }): Promise<unknown>;
  };
}

async function setStatus(
  context: Parameters<ActionHandler<CurrentUser>>[0],
  status: AppointmentStatus,
) {
  if (!context.id) {
    return { ok: false, message: "Missing appointment id." };
  }

  const db = context.db as ScopedAppointmentClient | undefined;
  if (!db) {
    return { ok: false, message: "Database client unavailable." };
  }

  await db.appointment.update({
    where: { id: context.id },
    data: { status },
  });

  return {
    ok: true,
    message:
      status === "ATTENDED"
        ? "Appointment marked as attended."
        : "Appointment cancelled.",
  };
}

/**
 * Handlers run on the server with the scoped Prisma client, so an appointment
 * from another clinic is not reachable even if the id is guessed.
 */
export const resourceActions: Record<
  string,
  Record<string, ActionHandler<CurrentUser>>
> = {
  Appointment: {
    attend: (context) => setStatus(context, "ATTENDED"),
    cancelAppointment: (context) => setStatus(context, "CANCELLED"),
  },
};
```

El `db` del contexto es Prisma extendido con el scope de la política. Una cita
de otra clínica no es alcanzable aunque alguien adivine su id.

## Problemas frecuentes

- **`init` rechaza la tenencia**: necesita un schema sin modelos de auth. Parte
  de un scaffold nuevo o añade los campos de organización a mano.
- **Listas vacías**: toda política devuelve `null` sin organización. Comprueba
  que el usuario tiene una y que el selector muestra una clínica.
- **Falta una acción propia**: el nombre choca con un integrado (`cancel`,
  `delete`, `save`...). Renómbrala.
- **Tipos de Prisma desactualizados**: ejecuta `pnpm prisma generate` después de
  cada cambio de schema.

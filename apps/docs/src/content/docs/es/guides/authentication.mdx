Dashild no incluye una librería de autenticación. El panel necesita dos cosas de
la app:

```ts
export const panel = definePanel({
  // ...
  auth: {
    getCurrentUser,
    signOut, // opcional
  },
});
```

`getCurrentUser` se ejecuta en el servidor y devuelve el usuario con sesión o
`null`. `signOut` es opcional; cuando existe, el menú de usuario muestra la
acción de cerrar sesión.

## Better Auth

```bash
pnpm dashild init --auth better-auth --yes
```

Escribe:

```text
src/lib/auth.ts
src/lib/auth-client.ts
src/lib/session.ts
src/lib/auth-actions.ts
src/lib/email.ts
src/app/api/auth/[...all]/route.ts
src/app/login/page.tsx
src/app/signup/page.tsx
src/app/forgot-password/page.tsx
src/app/reset-password/page.tsx
src/components/dashild/login-form.tsx
src/components/dashild/signup-form.tsx
src/components/dashild/forgot-password-form.tsx
src/components/dashild/reset-password-form.tsx
```

Las carpetas son condicionales: si la app ya tiene `lib/` y `components/` en la
raíz en vez de bajo `src/`, los ficheros van allí. El directorio `app` sigue la
misma regla.

También añade `better-auth` a `package.json`.

### Modelos de Prisma

Si el esquema no tiene ninguno de `User`, `Session`, `Account` o `Verification`,
`init` añade los cuatro. Si encuentra **cualquiera** de ellos, no añade ninguno y
avisa; adapta los modelos existentes tú mismo. La comprobación es todo o nada.

## Entorno

`create-dashild` escribe `.env` y un `.env.example` versionado. `dashild init`
solo añade claves que falten a `.env.example`; nunca escribe `.env`.

| Variable | Dónde | Para qué |
| --- | --- | --- |
| `DATABASE_URL` | `.env` y `.env.example` | Conexión de la app y de Prisma. |
| `DIRECT_URL` | `.env` si se facilita; placeholder comentado en `.env.example` | URL sin pooler para migraciones. |
| `BETTER_AUTH_SECRET` | Con Better Auth | Firma de sesión. Genérala con `openssl rand -base64 32`. |
| `BETTER_AUTH_URL` | Con Better Auth | Origen público; debe coincidir con la URL del navegador. |
| `ALLOW_SIGNUP` | Con Better Auth | `false` cierra el registro público. |
| `REQUIRE_EMAIL_VERIFICATION` | Con Better Auth | `true` exige el enlace de verificación. |
| `RESEND_API_KEY` | Solo en `.env.example`, comentada (Better Auth) | Si existe, `sendEmail` envía por Resend. |
| `EMAIL_FROM` | Solo en `.env.example`, comentada (Better Auth) | Remitente de Resend. |

Las claves de email nunca se escriben en `.env`: descoméntalas allí (o añádelas
al entorno de despliegue) cuando configures un proveedor.

`BETTER_AUTH_URL` debe coincidir con el origen que abres en el navegador. Un
desajuste hace que el login falle con un error de origen.

## Registro, verificación y reset

- `ALLOW_SIGNUP=false` desactiva la API de registro y la página de signup muestra
  “Sign-up disabled”. Crea usuarios desde tu propio flujo de administración.
- `REQUIRE_EMAIL_VERIFICATION=true` envía el enlace de verificación al
  registrarse y bloquea el login hasta verificar el email.
- `/forgot-password` pide un enlace de reset; `/reset-password?token=...` fija la
  nueva contraseña.
- El rate limit está activo (100 peticiones por minuto) en la configuración
  generada.

## Email

`src/lib/email.ts` usa Resend cuando existe `RESEND_API_KEY`:

```ts
await fetch("https://api.resend.com/emails", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.RESEND_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    from: process.env.EMAIL_FROM ?? "Dashild <onboarding@resend.dev>",
    to,
    subject,
    text,
  }),
});
```

Sin clave, registra el email en desarrollo y lanza un error en producción, para
que el reset y la verificación no pierdan correos en silencio. Sustitúyelo por
Postmark, SES o tu propio transporte si lo prefieres.

## Tu propia auth

Usa el modo por defecto y rellena el adaptador:

```bash
pnpm dashild init --auth none --yes
```

```ts
async function getCurrentUser(): Promise<CurrentUser | null> {
  const session = await myAuth.getSession();
  if (!session) return null;

  return {
    id: session.user.id,
    email: session.user.email,
    name: session.user.name,
    organizationId: session.user.organizationId,
    roles: session.user.roles,
  };
}
```

`CurrentUser` exige `id`; `email`, `name`, `organizationId` y `roles` son
opcionales. Devolver `organizationId` y `roles` basta para las
[políticas](/es/guides/policies/).

Si el esquema ya tiene algún modelo de Better Auth, `init --auth better-auth` no
modifica el esquema; avisa y deja la adaptación en tus manos.

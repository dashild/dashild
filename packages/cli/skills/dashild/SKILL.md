# Dashild

Dashild is an admin layer for Next.js + Prisma. A **resource** is a data file;
one catch-all route renders every resource. Security is resolved on the server
from `policies.ts`. Never generate a page per model and never put a `where` in a
resource.

Use this skill when the task involves building or extending a Dashild panel.
Read the project state before writing code.

## Read first

1. `package.json` (installed `@dashild/*` version).
2. `prisma/schema.prisma`.
3. `src/dashild/panel.ts`, `policies.ts`, `actions/index.ts`, `runtime.ts`,
   `server.ts`, `src/lib/session.ts`.
4. `dashild.json` (template, auth, route, stack version).

If the project has no Dashild yet, scaffold it with
`pnpm create dashild@latest <name>` or add it with `pnpm dashild init --auth better-auth --yes`.
For tenancy use `--tenancy` (requires Better Auth and a schema without auth
models).

## Workflow

1. **Understand the domain.** Ask for the entities, fields, relations, roles,
   whether rows belong to a tenant/author, and which workflow actions matter
   (publish, approve, assign...). Do not invent requirements.
2. **Propose the model.** List Prisma models, relations, and the resources you
   will create. Confirm before writing.
3. **Write the schema.** Use `String @id @default(uuid())`, `createdAt`,
   `updatedAt`, enums for statuses, explicit `organizationId`/`authorId` when
   scoping. Run:
   ```bash
   pnpm prisma migrate dev --name <change>
   pnpm prisma generate
   ```
   `migrate dev` writes and applies the migration, but it does **not** regenerate
   `dashild-metadata.json` on Prisma 7.10; run `prisma generate` or
   `make:resource` will not see the new models.
4. **Generate resources** with the CLI, then edit them:
   ```bash
   pnpm dashild make:resource Customer
   ```
   It writes `src/dashild/resources/customer.ts`, registers it in `panel.ts`,
   and adds a **fail-closed** policy entry (`scope: () => null`). The command is
   write-once.
5. **Write policies.** Replace the fail-closed entries with real scope and
   permissions. See `references/policies.md`.
6. **Add actions only when the workflow needs them.** Declare them in the
   resource and implement the handler in `src/dashild/actions/index.ts`. See
   `references/actions.md`.
7. **Seed demo data.** Add `prisma/seed.ts` and a `db:seed` script. Use Better
   Auth's `signUpEmail` for users so passwords and `Account` rows are created
   correctly. Keep it re-runnable and wrap the work in `main()`; see
   `references/seed.md`.
8. **Verify.** Run `pnpm dashild doctor` and `pnpm build`; fix every error
   before reporting done. Then describe what to click and with which role.

## Hard rules

- **`type: "select"` for enums in forms.** `type: "enum"` is only for filters.
- **Never name a custom action `create`, `view`, `edit`, `delete`, `save`, or
  `cancel`.** Those are built-in names; the panel ignores yours.
- **Declaring `table.actions` replaces the built-ins.** List `create`, `view`,
  `edit`, and `delete` explicitly if you still want them.
- **`scope` returns a `where` object or `null`.** Never `undefined` (a forgotten
  `return` allows everything). Returning `null` denies the resource.
- **`create` is not constrained by the scope.** Set `organizationId`/`authorId`
  from the authenticated server context, never from a browser field.
- **Fail closed:** a resource without `policy`, without an entry in
  `policies.ts`, or with `scope: null` is denied.
- **One route, no page generator.** Do not create `app/admin/<model>/page.tsx`.
- **The resource is data.** Logic belongs in policies, actions, or registered
  components.
- **Use the scoped client** (`db` in action handlers, `runtime.client(user)` in
  custom server code); do not import Prisma directly for tenant data.
- **Do not hand-edit generated glue without a reason.** It is app code, but it
  was generated by `dashild init`; keep the marker line.
- **After any schema change:** `pnpm prisma migrate dev` **and**
  `pnpm prisma generate`. The migration does not regenerate the metadata.
- **UI templates:** `pnpm dashild ui:add avatar-cell --dir src/components/dashild`.
  The default folder is `components/dashild` at the project root.
- **Verification is mandatory:** `dashild doctor` and `build` must pass.

## Decisions

- **Tenant?** If rows belong to an organization, `dashild init --tenancy` or the
  `saas` starter; then every model gets `organizationId` and
  `scope: { organizationId }`. The sidebar switcher is generated.
- **Roles?** `CurrentUser.roles` (from your session) + `hasRole(ctx, ...)`.
  Keep role names in the app; the framework does not define them.
- **Author ownership without tenants?** Scope by `{ authorId: ctx.user.id }`
  and give admins `{}` (see the `blog` starter).
- **Relations?** o2m uses a relation manager; m2m uses a multi-select in the
  form. The child model needs its own resource.
- **Money?** `Decimal` + `format: "currency"`, `currency: "EUR"` (or your ISO
  code). Decimals cross the wire as strings; do not assume `number`.
- **Custom rendering?** A cell/field component via `registerCell` /
  `registerField`, or `ui:add` for a starting template.
